# Тестовый VPS — этап 2.3

## Сборка через GitHub Actions

Workflow `.github/workflows/images.yml` проверяет сборку интерфейса, типы и тесты сервера, затем собирает оба Docker-образа на GitHub. При отправке в `main` или ручном запуске из `main` он публикует их в GitHub Container Registry с тегом полного SHA коммита: `ghcr.io/ignitione1/stick-it-api:<SHA>` и `ghcr.io/ignitione1/stick-it-web:<SHA>`. Pull request только проверяет сборку, без публикации. Браузерные тесты в этот workflow пока не входят.

Новые пакеты GHCR могут быть закрытыми: перед получением образов на VPS проверьте их видимость и доступ. Для приватных пакетов понадобится отдельная авторизация только на чтение. Workflow не подключается к VPS, не обновляет контейнеры и не выполняет миграции: автоматический деплой и его секреты ещё предстоит настроить. Не публикуйте токены и содержимое `.env`.

Обновление VPS необходимо настроить только с ручным запуском через GitHub Actions (`workflow_dispatch`): отправка коммита может запускать проверки и сборку, но не деплой. При запуске оператор должен выбирать конкретную проверенную версию образов.

Сборка сохраняет кэш npm в GitHub Actions. По понедельникам в 03:00 по Красноярску отдельный workflow оставляет последний созданный кэш основной ветки и удаляет старые кэши Stick-it; если кэша основной ветки нет, очистка пропускается. Очистку можно запустить вручную. GitHub может запускать задания по расписанию с задержкой и самостоятельно удалять давно неиспользуемые кэши. Docker-кэш и артефакты сборки в Actions не сохраняются. Образы GHCR — версии приложения, а не кэш; для них нужна отдельная политика хранения с учётом отката.

Подготовлена конфигурация для Ubuntu Server LTS, 1 vCPU, 1 ГБ RAM, 20 ГБ SSD. VPS пока не предоставлен. Ни Docker, ни PostgreSQL на рабочем Windows-компьютере не устанавливаются. Рабочие локальные команды frontend/backend остаются прежними.

## Контейнеры

| Сервис | Образ/процесс | Сеть и данные | Лимит памяти |
| --- | --- | --- | --- |
| `web` | Официальный `nginx:stable-alpine`, непривилегированный `nginx`, готовый React `dist` | `127.0.0.1:8080` VPS → `8080`; сеть `frontend` | 64 МБ |
| `api` | Многоэтапный `server/Dockerfile`, официальный `node:24-bookworm-slim` (LTS), пользователь `node`, `node dist/index.js` | Только внутренний `3000`; `frontend` + `backend`; volume `/app/uploads` | 256 МБ, V8 heap 160 МБ |
| `postgres` | Официальный `postgres:17-bookworm`; major зафиксирован | Только сеть `backend` с `internal: true`, volume `/var/lib/postgresql/data`; порт не опубликован | 320 МБ |

Всего лимиты контейнеров — 640 МБ. Остальная память нужна ОС и Docker. Это начальные настройки, а не результаты нагрузочного теста. PostgreSQL: 20 соединений, shared buffers 64 МБ, work memory 2 МБ на операцию, maintenance 32 МБ, отключены JIT и параллельный gather; пул API — 5 соединений. `max_wal_size=256MB` — ориентир для checkpoints, не жёсткая квота размера БД/WAL. У приложений ограничены процессы; JSON-логи ротируются по 3 × 5 МБ на контейнер. Следите за `docker stats`, OOM и свободным диском. Контейнеры и базовые образы потребуют дополнительного дискового пространства.

`compose.yaml` содержит только готовые образы, без `build`: сборка на VPS не выполняется. `restart: unless-stopped` применяется к трём сервисам. Цепочка начального запуска: PostgreSQL healthy → API healthy → web. Healthcheck PostgreSQL проверяет TCP основного сервера, API — текущий `/api/health`, web — `/healthz`. Health API проверяет HTTP, а соединение с БД проверяется при его запуске. Healthcheck сам по себе не перезапускает unhealthy-контейнер: политика restart реагирует на завершение процесса. Проверяйте причины через логи.

Web/API имеют read-only root filesystem, временный `/tmp`, сброшенные capabilities и `no-new-privileges`; запись приложения предусмотрена только в volume загрузок. Новый uploads volume получает владельца `node` (UID 1000) из образа. Файлы не раздаются Nginx напрямую: API принимает вложения потоково и выдаёт их только авторизованным сотрудникам; см. [вложения](../server/docs/attachments.md). Пользовательские данные не включаются в образы.

## Сборка и доставка вне VPS

Нужна рабочая машина или CI с Docker; устанавливать Docker на текущий Windows специально для этого не требуется. Frontend можно собрать сейчас отдельно:

```sh
npm ci
npm run build
```

На машине с Docker из корня проекта:

```sh
# Для x86_64 VPS; для aarch64 используйте linux/arm64 и подходящий builder.
sh deploy/scripts/build-images.sh 2.3.0 linux/amd64
docker save stick-it-api:2.3.0 stick-it-web:2.3.0 | gzip > stick-it-2.3.0.images.tar.gz
```

Скрипт проверяет наличие `dist/index.html`, собирает backend в Linux build-stage и Nginx из уже готового `dist`. Production-stage backend содержит только скомпилированный код, production npm-зависимости и существующие SQL-миграции; компилятор и Drizzle Kit туда не копируются. `.dockerignore` обоих контекстов разрешают только нужные входы, исключая `.env`, node_modules, тесты и бэкапы. Для сборки образов секреты не нужны.

Версия CPU образов должна совпадать с VPS (`uname -m`). Повторное использование тега может давать разные базовые patch-версии: сохраняйте готовые release-образы, для строгой воспроизводимости фиксируйте digest базовых образов после их проверки. На сервер передаётся `docker save`-архив или образы через registry. Альтернатива архиву: `docker tag`, `docker push`, затем выставить `API_IMAGE`/`WEB_IMAGE` на registry-теги и выполнить `docker compose pull`. Пароли registry не помещаются в репозиторий.

## Первичная подготовка Ubuntu

1. Подключитесь по известному SSH-адресу под своим пользователем с sudo. VPS в этой задаче не создаётся и удалённые команды сейчас не выполняются.
2. Установите Docker Engine и Compose plugin по [официальной инструкции для Ubuntu](https://docs.docker.com/engine/install/ubuntu/). Команды ниже используют `sudo`; добавление пользователей в Docker-группу не требуется.
3. Проверьте `sudo docker version`, `sudo docker compose version` (Compose v2.20+), `uname -m`, `free -m`, `df -h`.
4. Создайте каталог выпуска, например `/opt/stick-it`, с доступом вашему deploy-пользователю. Передайте туда `compose.yaml`, весь `deploy/` и архив готовых образов. Исходники frontend/backend и npm на VPS для работы не нужны. Для следующего выпуска используйте те же пути и имена volumes.

Пример доставки со своей машины (замените `DEPLOY_USER` и `VPS_HOST`):

```sh
scp compose.yaml stick-it-2.3.0.images.tar.gz DEPLOY_USER@VPS_HOST:/opt/stick-it/
scp -r deploy DEPLOY_USER@VPS_HOST:/opt/stick-it/
scp .env.example DEPLOY_USER@VPS_HOST:/opt/stick-it/.env.example
```

На VPS:

```sh
cd /opt/stick-it
sudo docker load -i stick-it-2.3.0.images.tar.gz
umask 077
# Только при отсутствии собственного .env:
cp -n .env.example .env
chmod 600 .env
# Init-скрипт должен читаться пользователем postgres внутри контейнера.
chmod 644 deploy/postgres/10-app-role.sh
```

Заполните `.env` редактором. Получите **два разных** пароля командой `openssl rand -hex 32` дважды, не используйте примерные пароли. Один — `POSTGRES_ADMIN_PASSWORD`, другой — `POSTGRES_APP_PASSWORD`. В `DATABASE_URL` укажите второй пароль, `POSTGRES_APP_USER`, host `postgres`, port `5432` и `POSTGRES_DB`. Hex-пароль не требует URL-encoding; прочие специальные символы пароля нужно кодировать. Не вставляйте секрет в командную строку shell. Не публикуйте вывод `docker compose config` или `docker inspect`: там есть окружение контейнеров. Для проверки используйте `config --quiet`.

Для Web Push нужны постоянные `VAPID_PUBLIC_KEY` и `VAPID_PRIVATE_KEY`. Их можно заранее создать в рабочем каталоге разработчика командой `npm --prefix server run push:keys`; значения записываются в защищённый игнорируемый `.local/push-vapid.env`. Передайте их на сервер по защищённому каналу и заполните `.env`, не записывая приватный ключ в репозиторий или логи. Без ключей доска работает, но push отключены. Инструкция по ограничениям HTTPS и браузеров — в [описании push](../server/docs/push.md).

`POSTGRES_APP_USER` должен начинаться с латинской строчной буквы, содержать только `[a-z0-9_]`, иметь не более 63 символов и не быть `postgres`/`pg_*`. Он создаётся с `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION`; эта роль владеет БД и может применять схему приложения. Администратор кластера — отдельный `postgres` с отдельным паролем. Переменные пароля меняют первоначальную инициализацию, а не пароль уже существующей роли: простое редактирование `.env` не ротирует пароль в существующей БД.

Скрипт `10-app-role.sh` официальный entrypoint запускает только при первой инициализации пустого PostgreSQL volume. Данные не пересоздаются при рестарте. После ошибки частичной инициализации сначала выясните причину: не удаляйте volume, если там могут быть нужные данные. Имена `POSTGRES_VOLUME_NAME`/`UPLOADS_VOLUME_NAME` определяют хранилища; изменение имени подключит другое хранилище, не перенесёт данные.

Для уже существующей установки сохраните прежние `COMPOSE_PROJECT_NAME`, `POSTGRES_VOLUME_NAME`, `UPLOADS_VOLUME_NAME`, имя базы и роль в её `.env`: новые примеры используют имена Stick-it и не переименовывают существующие данные.

## Первый запуск и ручные миграции

```sh
cd /opt/stick-it
sudo sh deploy/scripts/stack.sh check
sudo sh deploy/scripts/stack.sh db-up
# Явный запуск оператором; сначала проверить SQL первой миграции в репозитории.
sudo sh deploy/scripts/stack.sh migrate
# Первоначальная настройка двух администраторов из BOOTSTRAP_ADMIN_* в .env:
sudo docker compose -f compose.yaml -f deploy/compose.bootstrap.yaml run --rm --no-deps api
sudo sh deploy/scripts/stack.sh up
sudo sh deploy/scripts/stack.sh status
curl --fail http://127.0.0.1:8080/api/health
```

Эквивалент миграции: `sudo docker compose run --rm --no-deps --entrypoint node api dist/db/migrate.js`. PostgreSQL должна быть запущена заранее. Команда проверяет конфигурацию и SQL-файлы до соединения, затем проверяет реальные `current_database/current_user` и отсутствие superuser-привилегий. Допускается только Compose-host `postgres:5432` и выбранная пара базы/роли; URL с дополнительными параметрами отклоняется. Advisory lock предотвращает одновременные миграции через эту команду. Мигратор Drizzle использует существующий журнал, применяет SQL в транзакции, не делает `drop`, `push`, reset или генерацию схемы на VPS. API при запуске миграции не выполняет. Не смешивайте параллельный запуск с отдельным Drizzle Kit вне этой блокировки.

Первую миграцию применяют к пустой БД. Для обновлений сначала сделайте бэкап, остановите API/web, доставьте новую пару образов, затем явно выполните миграцию и запустите сервисы. Не редактируйте уже применённые SQL-файлы. Откат образа не откатывает схему; несовместимое изменение требует отдельного плана восстановления. Локальная команда `npm --prefix server run db:migrate` с Drizzle Kit сохранена для известной локальной БД; контейнерный вариант не требует dev-зависимостей.

Проверьте конфигурацию и права каталога загрузок:

```sh
sudo docker compose exec -T web nginx -t
sudo docker compose exec -T api node -e 'require("node:fs").accessSync(process.env.UPLOAD_DIR, require("node:fs").constants.W_OK)'
sudo docker compose ps
sudo docker stats --no-stream
sudo ss -lnt
```

Ожидается только `127.0.0.1:8080` для приложения, без опубликованных 3000/5432. HTTP_PORT меняет номер, но не loopback-привязку. При изменении существующего uploads volume с другими владельцами нужно отдельно проверить/исправить его права; образ не меняет рекурсивно права существующих данных.

## Доступ к закрытому стенду

На своём компьютере держите SSH-туннель:

```sh
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:8080:127.0.0.1:8080 DEPLOY_USER@VPS_HOST
```

Откройте `http://127.0.0.1:8080`. Если локальный порт занят, замените первое `8080` на свободный и задайте соответствующий `APP_ORIGIN` в `.env`. Порты 80/443/8080 не нужно открывать в cloud firewall; допускайте SSH только по своей политике доступа. Вход сотрудников реализован, но стенд остаётся закрытым и без TLS. Сохраняйте loopback-привязку и SSH-туннель; внешний reverse proxy не должен случайно публиковать этот стенд. Для текущего HTTP задайте `COOKIE_SECURE=false`; для будущего HTTPS — true и соответствующий HTTPS Origin. [Учётные записи и профиль](../server/docs/accounts.md).

Nginx раздаёт SPA, возвращает 404 для отсутствующих `/assets/*`, сохраняет `/api/` при proxy_pass, передаёт Host/адрес/протокол. Заданы базовые security headers и общий лимит тела 26 МиБ. API ограничивает вложения: до 5 файлов, до 10 МиБ каждый и до 25 МиБ суммарно; маршруты входа/админки имеют меньшие лимиты. Для будущего SSE отключены buffering/cache/gzip и увеличен read timeout; сам SSE не реализован. Compose задаёт `TRUST_PROXY=one`, поскольку API доступен только из внутренних сетей через один Nginx. Nginx перезаписывает X-Forwarded-For адресом непосредственного клиента. При другой топологии пересмотрите доверие прокси.

Вход, сотрудники, отделы, профиль и записки работают через сервер. Изменение origin/порта создаёт другое пространство localStorage только для прежней локальной копии; серверная доска от этого не меняется. Перед первичным bootstrap заполните два набора BOOTSTRAP_ADMIN_* в корневом `.env`; обычному API эти секреты не передаются. После создания начальные пароли можно убрать. [Общая доска и два администратора](../server/docs/shared-board.md).

## Управление

```sh
sudo sh deploy/scripts/stack.sh logs    # Ctrl+C завершает только просмотр
sudo sh deploy/scripts/stack.sh status
sudo sh deploy/scripts/stack.sh stop
sudo sh deploy/scripts/stack.sh up
sudo sh deploy/scripts/stack.sh down    # Удаляет контейнеры/сети, сохраняет volumes
```

Не используйте `down -v`, `docker volume prune` или очистку каталогов БД для обычного обновления. Скрипт `down` не передаёт дополнительные аргументы и не удаляет volumes. Для SIGTERM API предусмотрено 20 секунд до принудительной остановки Docker; внутренний graceful shutdown ограничен 15 секундами. Nginx получает SIGQUIT. Логи идут в stdout/stderr, а не в растущие файлы внутри приложения.

## Резервное копирование

Volume обеспечивает постоянство данных, **не резервную копию**. Скрипт временно останавливает работающие API/web, делает согласованный комплект БД + файлов, затем возвращает только ранее работавшие сервисы. PostgreSQL продолжает работать. На стенде пока нет других писателей; если они появятся, их тоже нужно остановить.

```sh
sudo sh deploy/scripts/backup.sh /opt/stick-it/backups
```

Создаётся каталог с UTC-датой и PID: `database.dump` (pg_dump custom format без owner/ACL), `uploads.tar.gz` и `SHA256SUMS`. На время операции нужны свободный диск и короткий простой. Незавершённые файлы имеют `.part`, они не считаются пригодным комплектом. Пароль не передаётся в argv, имена файлов или историю shell: pg_dump подключается локально внутри PostgreSQL-контейнера. Tar работает как `node`, тот же пользователь, которому принадлежат файлы приложения; дополнительные root-права/capabilities не выдаются. Скрипт возвращает остановленные контейнеры через `compose start --wait`, не пересоздаёт их с потенциально другими тегами из `.env`.

Каталог создаётся с закрытыми правами. Скопируйте весь готовый комплект **за пределы VPS** по защищённому каналу и проверьте `sha256sum -c SHA256SUMS` на принимающей машине. При копировании через обычного SSH-пользователя сначала выдайте ему ограниченный доступ к выбранной копии, не делайте бэкапы общедоступными. Храните конфигурацию `.env` отдельно в защищённом/зашифрованном хранилище; дамп не включает пароли ролей PostgreSQL. Сохраняйте соответствующие release-образы. Внешнее хранилище, расписание и удаление старых копий автоматически не настраиваются.

## Восстановление

Проводите восстановление в отдельные **пустые** volumes и известную базу, сохранив оригинальные данные. Для пробного восстановления задайте новые `COMPOSE_PROJECT_NAME`, имена двух volumes и свободный HTTP_PORT в отдельном каталоге/`.env`. Используйте имена БД/роли, ожидаемые данным комплектом приложения, и свои новые пароли. Загрузите нужные release-образы, проверьте конфигурацию, запустите только PostgreSQL:

```sh
sudo sh deploy/scripts/stack.sh check
sudo sh deploy/scripts/stack.sh db-up
# До restore НЕ запускайте migrate: цель должна оставаться пустой.
sudo sh deploy/scripts/restore.sh /path/to/trusted-backup-directory
sudo sh deploy/scripts/stack.sh up
curl --fail http://127.0.0.1:8080/api/health
```

Скрипт сверяет checksums, останавливает API/web, отказывается работать с непустой БД или uploads volume, восстанавливает дамп одной транзакцией под ролью приложения и извлекает файлы. Только доверенные собственные бэкапы: tar/SQL из неизвестного источника исполнять нельзя. Файлы извлекаются как `node` с `--no-same-owner`, чтобы принадлежать приложению на новом хосте; затем проверьте доступ API к `/app/uploads` и содержимое БД. Сервисные роли создаёт init-скрипт, а не pg_dump; `--role`, `--no-owner` и `--no-acl` назначают восстановленные объекты приложению.

После восстановления API/web остаются остановленными до явного `up`. Если восстановление файлов после БД завершилось ошибкой, не запускайте приложение с неполным комплектом: выясните причину и повторите в новых пустых volumes. Скрипт ничего не очищает и не удаляет. Проверка `/api/health` подтверждает HTTP и запуск сервера, но не полноту восстановленных данных; нужно также проверить таблицы, историю миграций и файлы. Тест восстановления на VPS обязателен перед использованием бэкапов как рабочего процесса.

Проверены YAML-синтаксис/структура Compose, отсутствие опубликованных портов API/PostgreSQL, относительные входы Dockerfile, параметры мигратора и неизменность frontend по SHA-256. Shell-скрипты проверяются через `sh -n` в имеющемся Git Bash. Реальная БД этим тестам не нужна.

На текущей машине Docker отсутствует: не выполнялись `docker compose config`, контейнерные сборки, `nginx -t`, Linux runtime, инициализация PostgreSQL, SQL-миграция, backup/restore и измерение памяти на VPS. Их статическая проверка не заменяет запуск контейнеров. Реальные секреты не создавались, VPS не подключался, системные настройки Windows не менялись.

Справочные источники: [Compose services/ports/healthchecks](https://docs.docker.com/reference/compose-file/services/), [официальный PostgreSQL image](https://hub.docker.com/_/postgres), [Nginx proxy directives](https://nginx.org/en/docs/http/ngx_http_proxy_module.html), [Node.js releases](https://nodejs.org/en/about/previous-releases).
