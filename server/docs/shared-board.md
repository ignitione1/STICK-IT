# Общие записки и два администратора

Дополнение: [фото, 12 аватаров, 10 дизайнов бумаги и независимые крепления](profile.md).

Учётные записи, профили и записки работают через Fastify/PostgreSQL. На рабочих страницах localStorage больше не является источником записок: изменения доступны другим сотрудникам и после входа с другого компьютера.

## Два администратора из env

Для локальной разработки заполните в `server/.env`:

```env
BOOTSTRAP_ADMIN_1_LOGIN=
BOOTSTRAP_ADMIN_1_NAME=
BOOTSTRAP_ADMIN_1_PASSWORD=
BOOTSTRAP_ADMIN_2_LOGIN=
BOOTSTRAP_ADMIN_2_NAME=
BOOTSTRAP_ADMIN_2_PASSWORD=
```

Укажите два разных логина и собственные пароли от 12 до 128 символов. Пример не содержит рабочих секретов. После настройки `DATABASE_URL` и ручного применения миграций выполните из корня:

```powershell
npm.cmd --prefix server run admin:bootstrap
```

Команда создаёт недостающих администраторов в БД с хешами Argon2id, максимум два admin-аккаунта суммарно. Уже существующему администратору не меняются имя, пароль, роль, активность или отделы. Обычный сотрудник с занятым логином не повышается до администратора; конфликт прерывает транзакцию. Пустые/неправильные данные новых администраторов откатывают всю операцию. Изменение env не сбрасывает пароль действующего аккаунта.

После создания пароли BOOTSTRAP можно удалить: повторный запуск с сохранёнными LOGIN/NAME оставит имеющиеся аккаунты без изменений. Пароли обязательны только для новых аккаунтов. Если раньше администратор был создан интерактивной командой, один из логинов env должен совпадать с ним, чтобы не создавать третьего. Следующих администраторов через UI/API создавать или повышать из user нельзя. Оба администратора входят через обычные сессии и далее добавляют сотрудников в БД.

Для размещения записок администратор, как и сотрудник, должен иметь активный отдел. Bootstrap создаёт общую доску, но не придумывает отделы: войдите, создайте отдел и назначьте его администраторам через управление командой.

### Docker Compose

На VPS bootstrap-поля заполняются в корневом `.env`. После загрузки новых образов и `db-up`/`migrate` оператор явно запускает:

```sh
sudo docker compose -f compose.yaml -f deploy/compose.bootstrap.yaml run --rm --no-deps api
```

Override добавляет bootstrap-переменные только одноразовому контейнеру. Обычный `compose.yaml` их в API не передаёт; они не копируются в образы. При обычном старте никаких аккаунтов или миграций автоматически не создаётся. Секреты не указываются аргументами shell и не выводятся в лог. Существующая интерактивная команда `admin:create` оставлена для совместимости, но основной способ первоначальной настройки — `admin:bootstrap`.

## Записки

- Создание сохраняет текст, доску, автора из сессии, снимок его отдела, выбранный пресет и seed бумаги. Отправить от чужого имени нельзя. Последующие изменения профиля/членства не меняют сохранённые ID отдела, пресет и seed старой записки.
- Получателями могут быть сотрудники (несколько), отделы (несколько) или отдел выбранной доски. У общей доски «Всем сотрудникам» сохраняет список активных сотрудников **на момент отправки**. У отдела получателями считаются его текущие участники. Это адресация для отметок, не ограничение просмотра: все вошедшие сотрудники видят все доски и архив.
- Ответ ссылается на основной стикер и получает очередной `reply_order` под блокировкой доски. Ответ на ответ тоже входит в эту цепочку; по умолчанию адресуется автору той записки, на которую нажали «Ответить». FK запрещают циклы и другую доску.
- Все вошедшие сотрудники могут перемещать основную записку и поднимать её группу. Абсолютные X/Y сохраняются только у корня, ответы сохраняют смещения. Порядок наложения общий (`z_index`), выделение/перемещение поднимает всю группу. Одновременные перемещения сериализуются по строке доски; последняя принятая позиция становится общей.
- Менять текст и восстанавливать записку может только автор. Администратор также может архивировать чужие записки, но не редактировать их.
- Отметки меняет автор или адресат. «Готово» требует «Прочитано»; снятие read атомарно снимает done и очищает четыре поля автора/времени отметок. Повторная установка не переписывает прежнего автора/время.
- Для текста, галочек и архивирования передаётся `revision`. При устаревшей версии сервер возвращает 409; интерфейс сохраняет набранный текст в открытом редакторе и сообщает об ошибке вместо молчаливой перезаписи. Позиции и подъём слоя не меняют revision текста/отметок.

Обновления запрашиваются раз в пять секунд, при фокусе окна и после собственной операции. Во время перетаскивания и сохранения опрос не перезаписывает локальное положение. Ошибки видны над доской, есть кнопка повторной загрузки. При недоступности сервера изменения не записываются в отдельную скрытую локальную доску. WebSocket/SSE не используются; раздел «Уведомления» показывает непрочитанные адресованные записки из общего состояния. Для новых записок и ответов сервер также отправляет [Web Push](push.md) активным подпискам получателей.

Звук уведомлений включается кнопкой под «Уведомлениями»; включение проигрывает образец. Используется локальный MP3 классического ICQ «Uh-oh»; [источник записи](../../docs/notification-sound.md). По умолчанию звук включён; явное отключение сохраняется. Выбор хранится в браузере отдельно для каждого аккаунта. После перезагрузки браузер разрешает воспроизведение только после клика или нажатия клавиши в приложении. Первая загрузка, собственные и неадресованные записки, архив, редактирование и повторное снятие отметки «Прочитано» не озвучиваются. Без push звук следует опросу, который приостанавливается в скрытой вкладке. С push возможны системные уведомления при закрытой вкладке; звук ICQ доступен открытой вкладке после действия пользователя.

## Архив

Это сохранение данных, не DELETE. Архивирование основного стикера скрывает с активной доски всю группу, не меняя собственные архивные поля ответов. Архивирование ответа скрывает только ответ. Пока оригинал активен, такой ответ показывается самостоятельной карточкой с коротким контекстом и ссылкой на исходную записку; активный оригинал не становится карточкой архива. При архивировании корня совпавшие с фильтрами ответы показываются вместе с ним, включая архивированные отдельно; их собственный статус не меняется.

Администратор может безвозвратно удалить совпавшие с фильтрами записки выбранной доски (до 100 записок за операцию). Перед подтверждением показывается итоговое количество с учётом ответов: удаление основной записки всегда включает все её ответы, даже не совпавшие с фильтрами. Отдельный ответ удаляется самостоятельно. Сервер проверяет архивное состояние, состав цепочки и ревизии; метаданные удаляются транзакционно, файлы — после фиксации. При сбое файловой системы в хранилище могут остаться осиротевшие файлы; сообщение записывается в журнал.

Автор может вернуть свою явно архивированную записку. Если архивирован корень, сначала его автор возвращает корень; отдельно архивированный ответ остаётся в архиве до действия своего автора. Записки удалённого отдела доступны в архиве, но восстановить их на закрытую доску нельзя.

Вход в архив показывает стопки по доскам отделов, включая общую доску и удалённые отделы. Стопка показывает количество совпавших записок; её выбор раскрывает карточки в сетку с короткой анимацией. «Все отделы» сворачивает сетку обратно. Выбор отдела также доступен отдельным фильтром «Отдел архива»; это доска записки, а не отдел её автора. Анимация отключена при prefers-reduced-motion.

Сохраняются поиск и фильтры по отправителю, личному получателю или отделу-получателю и **дате создания**. Фильтры адресатов используют сохранённые связи; историческое членство сотрудников не реконструируется. Если совпал ответ, скрытый вместе с корнем, архивированный корень добавляется как часть цепочки. Активные оригиналы не добавляются в сетку. Фильтры включают удалённые отделы и заблокированных сотрудников. API читает общее состояние в согласованной read-only repeatable-read транзакции.

## Старая локальная копия

Ключ `stickerboard:v1` не удаляется и не перезаписывается серверной синхронизацией. Если он найден, интерфейс предлагает скачать точную JSON-копию (в том числе при повреждённом JSON). Скрытие сообщения сохраняет отдельный флаг, не меняет саму копию.

Можно явно перенести собственные основные записки с совпадающим ID автора и действующей UUID-доской. Они публикуются с текущими профилем/отделом, без прежних отметок; текст, seed и координаты переносятся. Ответы и заметки других авторов автоматически не публикуются под вашим именем. Старые demo-ID отделов не сопоставляются с новыми UUID по догадке. Полная исходная информация остаётся в JSON. Современные UUID сохраняются, строковые legacy-ID получают стабильный UUIDv5 с учётом сотрудника: повтор публикации не создаёт дубликат. Уже существующая записка с другим текстом не перезаписывается. Экспортируйте копию перед переносом.

## API и миграция

| Метод | Назначение |
| --- | --- |
| `GET /api/stickers` | Все записки с признаками архива, адресатами и правами текущего сотрудника |
| `POST /api/stickers` | Создание или идемпотентный повтор с тем же UUID |
| `PATCH /api/stickers/:id` | Текст автора + revision |
| `PATCH /api/stickers/:id/marks` | read/done + revision |
| `PATCH /api/stickers/:id/position` | Абсолютная позиция корня |
| `POST /api/stickers/:id/raise` | Подъём группы |
| `PATCH /api/stickers/:id/archive` | Архивирование/возврат + revision |

Все методы требуют действующую сессию; изменения также требуют Origin и CSRF. Миграция `0002_shared_stickers.sql` добавляет revision с начальным значением 0, не удаляет данные. Существующие `0000` и `0001` не переписывались. Применение к постоянной БД выполняется вручную существующей командой миграций после проверки базы и резервного копирования.

Текущая реализация рассчитана на небольшой стенд: GET загружает общее состояние целиком, фильтры архива выполняются в интерфейсе. Перед ростом объёма данных нужно добавить серверную пагинацию/фильтрацию и проверить нагрузку на VPS. Реализованы загрузка/скачивание вложений и просмотр изображений; см. [вложения](attachments.md).

## Проверки

Серверные тесты выполняют все миграции и реальные запросы на PostgreSQL-движке PGlite. Проверяются идемпотентный bootstrap, запрет повышения ролей, адресаты/права, сброс отметок, конфликты revision, цепочки, координаты, архивирование и сохранение оформления при обновлении схемы. Браузерные тесты используют тот же Fastify и реальные сессии сотрудников, включая загрузку фото; состояние БД изолировано между сценариями. В тестах есть отдельный loopback endpoint сброса fixtures, находящийся только в `server/tests/browser-server.ts`, исключённом из production-сборки/Docker.

Постоянная PostgreSQL и Linux/Docker runtime на этом компьютере не настраивались. Тесты в памяти не заменяют проверку контейнеров, восстановления резервной копии и нагрузки перед запуском VPS.
