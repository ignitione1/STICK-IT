# Вход, управление командой и профиль

Актуальное дополнение: [два администратора из env и серверная общая доска](shared-board.md). Администраторов теперь создают отдельной командой, в UI можно создавать только обычных сотрудников. Записки уже хранятся на сервере; старый localStorage остаётся отдельной копией.

Регистрация закрытая. Администратор создаёт сотрудников, задаёт им имя, логин и пароль, назначает один или несколько отделов и основной отдел. Сотрудник выбирает готовый аватар или своё фото, один из десяти бумажных пресетов и независимое крепление; см. [правила профиля](profile.md). Пароль меняет/сбрасывает администратор. Произвольных цветов, шрифтов и параметров бумаги в профиле нет.

## Первый запуск локально

Для ручного стенда без PostgreSQL используйте `npm.cmd run dev:local` после установки зависимостей обоих пакетов; адрес — `http://127.0.0.1:5175`, пароли локальных администраторов — `.local/manual/local-admins.env`.

Для обычного API нужны зависимости обоих пакетов и собственная PostgreSQL. Docker и службы PostgreSQL автоматически не устанавливаются. Из корня репозитория:

```powershell
npm.cmd ci
npm.cmd --prefix server ci
# Скопируйте пример только при отсутствии собственного server/.env.
if (-not (Test-Path server/.env)) { Copy-Item server/.env.example server/.env }
```

Заполните `server/.env`: реальная `DATABASE_URL`, `APP_ORIGIN=http://127.0.0.1:5173`, `COOKIE_SECURE=false`, `TRUST_PROXY=none`. Origin указывается без пути и завершающего `/` и должен совпадать с адресом страницы в браузере. Для HTTP по loopback cookie Secure отключена явно; по умолчанию backend использует Secure. Для HTTPS установите `COOKIE_SECURE=true`.

После проверки выбранной базы вручную примените все миграции и создайте **двух** администраторов:

```powershell
npm.cmd --prefix server run db:migrate
npm.cmd --prefix server run admin:bootstrap
```

Команда читает LOGIN, NAME и PASSWORD двух администраторов из `BOOTSTRAP_ADMIN_1_*` и `BOOTSTRAP_ADMIN_2_*` в `server/.env`. Логин — от 3 до 64 латинских букв/цифр, допускаются точка, дефис и подчёркивание; регистр нормализуется. Новый пароль — от 6 до 128 символов; пароля по умолчанию нет. При повторном запуске существующие аккаунты остаются без изменений, даже если имя/пароль в env изменены. После создания начальные пароли можно удалить. Обычный пользователь с занятым логином не повышается до администратора. Одновременно создаётся общая доска, если её ещё нет.

Запустите в двух терминалах:

```powershell
npm.cmd --prefix server run dev
npm.cmd run dev
```

Откройте `http://127.0.0.1:5173`, войдите и выберите «Управление командой». Сначала создайте отдел, затем сотрудников. Первый администратор изначально без отделов; его можно назначить в созданный отдел через редактирование сотрудника. При создании отдела его доска создаётся той же транзакцией. Новая установка открывает пустые доски; демонстрационные пользователи автоматически не создаются.

## Действия администратора

- «Отделы»: создание, изменение имени/кода/цвета, удаление из активного списка. Код удалённого отдела остаётся занятым. Физического удаления отдела, доски или переписки нет: используется `departments.is_active = false`. Перед удалением надо перевести всех активных участников в другие отделы либо заблокировать их.
- «Сотрудники»: имя, логин, принадлежность к нескольким отделам и один основной отдел. Роль задаётся при первоначальном создании и не переключается в интерфейсе. Новые сотрудники имеют роль user, администраторы создаются командой из env. Сброс пароля — заполнить «Новый пароль»; пустое поле сохраняет существующий.
- Снятие «Учётная запись активна» блокирует вход, сохраняет историю и отзывает сессии. Смена пароля или роли также отзывает сессии. Нельзя отключить себя или последнего активного администратора. Проверки и изменения выполняются в транзакции под общей advisory-блокировкой.

Права проверяются backend на каждом запросе, не по видимости кнопок. Изменение имени, роли, логина, пароля или отделов через `/profile` отклоняется. Пользователь не может назначить себе роль администратора. Первый bootstrap — единственное исключение из требования назначить отдел при создании, чтобы администратор мог начать настройку пустой компании.

## Профиль

«Мой профиль» содержит 12 локальных рисованных аватаров с выбором мужских и женских образов, загрузку своего фото, десять готовых вариантов бумаги и четыре независимых крепления. Предпросмотр использует фактическую бумагу, узоры, крепления и тени приложения. Выбор сохраняется в базе и восстанавливается при следующем входе. Внешние URL аватаров не принимаются; см. [ограничения фото и правила оформления](profile.md).

Новые записки получают серверный снимок пресета и ID отдела автора плюс постоянный seed бумаги. Профиль не перекрашивает старые записки. Тексты, координаты, ответы, отметки и архив теперь сохраняются в PostgreSQL и синхронизируются между компьютерами. Прежний `stickerboard:v1` не перезаписывается: доступен экспорт и явный перенос своих основных записок. Повреждённая локальная копия не блокирует общую доску. Подробности — в [shared-board.md](shared-board.md).

## Сессии и защита

Пароли хешируются Argon2id (19 МиБ, 2 прохода, parallelism 1). Одновременно допускаются две операции хеширования/проверки, чтобы ограничить память небольшого VPS. Вход ограничен 10 запросами в минуту на IP; после пяти неверных паролей учётная запись блокируется для новых входов на 15 минут. Дополнительные неверные попытки продлевают блокировку. Администратор может сбросить пароль и счётчик. Сообщение входа одинаково для неизвестной, заблокированной учётной записи и неверного пароля.

Сессия — случайный 256-битный токен; в PostgreSQL хранится только SHA-256-хеш. Cookie `stickerboard_session` имеет `HttpOnly`, `SameSite=Strict`, путь `/api`, срок `SESSION_HOURS` (по умолчанию 720 часов, или 30 дней), опциональный Secure по конфигурации. При запросах авторизованного пользователя срок в базе и cookie продлевается не чаще раза в час; открытая вкладка также отправляет периодические запросы. Выход отзывает текущую сессию и удаляет cookie. Активность сотрудника, роль, срок и отзыв проверяются на сервере; интерфейс повторно проверяет сессию при фокусе окна и раз в минуту. Изменение `SESSION_HOURS` в существующем `.env` и перезапуск API необходимы отдельно; уже истёкшие сессии не восстанавливаются.

Изменяющие запросы требуют разрешённый Origin, `x-stickerboard-request: 1` и CSRF-токен текущей сессии. Вход требует Origin и специальный заголовок, чтобы исключить login-CSRF. CSRF-токен выдаётся в `/auth/me`/успешном входе и хранится только в памяти вкладки; bearer-токен и пароль в localStorage не записываются. Ответы модуля имеют `Cache-Control: no-store`; хеши паролей и токенов не входят в DTO. Логи не содержат тело запросов или исходные SQL-ошибки.

`TRUST_PROXY=none` — обычная локальная настройка. Compose задаёт `one`: доверие одному Nginx при внутреннем API без опубликованного порта; Nginx перезаписывает X-Forwarded-For адресом непосредственного клиента. При изменении топологии прокси настройку надо пересмотреть. Несколько пользователей одного SSH-туннеля/NAT могут делить один IP-лимит. Истёкшие/отозванные сессии перестают работать; отдельное расписание очистки старых строк пока не настраивалось.

## API

| Метод и путь | Доступ |
| --- | --- |
| `POST /api/auth/login` | Вход с Origin и специальным заголовком |
| `GET /api/auth/me` | Текущая сессия, профиль и CSRF |
| `POST /api/auth/logout` | Текущая сессия + CSRF |
| `GET /api/directory` | Любой активный сотрудник |
| `GET /api/profile/catalog` | Любой активный сотрудник |
| `PATCH /api/profile` | Собственные avatarId/avatarPhoto, paperStyle и fastening |
| `GET /api/profile/avatar/:id` | Фото сотрудника, только активная сессия |
| `GET/POST /api/admin/departments` | Администратор |
| `PATCH/DELETE /api/admin/departments/:id` | Администратор |
| `GET/POST /api/admin/employees` | Администратор |
| `PATCH /api/admin/employees/:id` | Администратор |

Открытого `/register` и просмотра паролей нет. Реализованы фото профиля и [вложения записок](attachments.md): защищённая загрузка/скачивание и просмотр изображений. API стикеров описан отдельно. К исходной схеме добавлены миграции `0001`–`0006`; оформление и фото описаны в [profile.md](profile.md), push — в [push.md](push.md). Уже применённые миграции не менялись.

## VPS

Соберите и доставьте новые образы, сделайте бэкап, вручную примените миграцию. На первой установке после `db-up` и `migrate`:

```sh
sudo docker compose -f compose.yaml -f deploy/compose.bootstrap.yaml run --rm --no-deps api
sudo sh deploy/scripts/stack.sh up
```

Для текущего закрытого HTTP-стенда через SSH `.env` содержит `APP_ORIGIN=http://127.0.0.1:8080` и `COOKIE_SECURE=false`; если локальный порт туннеля другой, Origin должен совпасть с ним. При будущем HTTPS — реальный HTTPS Origin и Secure=true. Существующая loopback-привязка Compose сохраняется; эта работа не публикует стенд в интернет. Создание первого администратора и миграции не запускаются автоматически.

## Проверки

```powershell
npm.cmd --prefix server run typecheck
npm.cmd --prefix server test
npm.cmd run build
npm.cmd run test:e2e
```

Серверные тесты исполняют все SQL-миграции, проверяют Argon2id, сессии, права, CSRF, блокировку и отзыв в PostgreSQL-движке PGlite в памяти. Браузерные тесты поднимают тот же Fastify с отдельной тестовой БД и Vite на портах 3101/5174, проверяют реальную форму входа, админку, профиль и действия с доской. Fixtures находятся только в `tests/`/`server/tests/` и исключены из production-контекста Docker; в рабочую БД тестовые сотрудники не добавляются. Системная PostgreSQL тестам не нужна.

Скриншоты входа, профиля и админки сохраняются в `.local/`. Контейнерные образы и подключение к постоянной PostgreSQL ещё требуют отдельной проверки на машине с Docker/известной БД; миграции на такую базу в этой задаче не применялись.
